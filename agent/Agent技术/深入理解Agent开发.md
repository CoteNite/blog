## 上下文工程

上下文是Agent的眼睛，它包含着Agent能够使用的所有信息，所有的外界信息必须载入到上下文中才可以被Agent使用

官方API的上下文可以分为以下几种：

- 系统提示词: 开发者编写，会被放置在上下文的最顶部，常常会用来定义Agent的行为规则，约束条件等内容，在训练的影响下会被视为最高的优先级
- 用户消息: 用户输入的内容
- 工具调用: 调用工具的结果，tool类消息的回复顺序往往和Agent发起的工具调用的顺序一致，且Tool类消息往往出现在模型回复后
- 模型回复: 模型的回复

目前所有的Agent，上下文都是将整个对话中的这四类消息全部发送给AI，而上下文工程就是对这四类消息处理

### ReAct与思维链

目前主流的AI回复方式是用户发起一次消息，AI进入思考，然后针对用户提出的要求发起一次或多次工具调用请求，接着根据返回的工具内容再次进入思考，判断是否要发起其他的工具请求或者退出思考直接返回给用户最终结果

这种形式来自22年的两篇经典论文[ReAct](https://arxiv.org/abs/2210.03629)和[Chain-of-Thought](https://arxiv.org/abs/2201.11903)，在早年些年（23年左右），这些功能往往需要智能体实现，而现在已经被LLM内化了

### Loop

Agent的核心是一个死循环，这个循环又被叫做Loop，最小的实现方式就是根据当前不同的api返回消息处理不同的事情，比如大模型返回的结果中出现了工具调用，Agent就去调用工具，然后返回结果给大模型，接着等待大模型的下一步指令，当大模型返回了所有的文本，则退出循环

### KVCache和Prompt Cache

KVCache是上下文工程必须要了解的一个前提，这里我们不过多简述底层，使用一种形象化的概述

大模型本质上是一个文本预测模型，他是根据前文的所有内容去预测下文的内容，其底层利用的Transformer与注意力机制导致其没输出一个新的文字，这个文字就会变成上下文的一部分，去影响下一个文字的预测，而下一个文字的预测，这是需要对之前的文字进行一个复杂的数学计算，这个计算可以简单的被理解为：要预测第n个文字，需要第n-1个文字与n-1之前的所有文字构成的一个高阶矩阵进行一个复杂的乘法，这一数学计算将会消耗很大的算力

由于大模型是无状态的，所以理论上大模型每吐出一个字，就要将上面的数学算法从第一个字开始完整的重新计算一边

所谓KVCache，就是将n-1之前的那部分中的部分文字对应的数学矩阵进行了缓存，让大模型每一次再进行矩阵乘法之前，不用再重新计算n-1之前的部分文字的矩阵，这节省了大量的算力

由于节省了大量的算力，也就导致缓存命中时的价格很低，这也是我们开发者关心的

那么如何提高缓存的命中率呢，根据KVCache的核心机制，他是从上下文的第一个字开始找对应的缓存，直到最后发现之前没有缓存过的文字，所以对应我们的上下文，我们应该**尽可能的让大模型的前置上下文不变**，这也是我们上下文工程的核心要求之一
